# yEgo 操作設計 v1（もち）

作成： 2026-11-11
根拠： プロジェクト計画書（2026-11-11）の利用場面①〜⑤と基本原則
担当範囲： アプリデザイン、スマートフォン／タブレット／iPad の操作設計。
機能（何ができるか）は Claude Code / Codex の機能設計に従い、本書は
「どう見せ、どう触らせるか」を定める。

## 1. 設計の前提（計画書から）

- 点検は現場作業。屋外・脚立上・片手・手袋があり得る
- 入力できるのは JSON で定義された欄だけ。それ以外は「変更できない」ことが見た目で分かること
- 文書は「編集前／作業中／編集後」を区別し、中断・誤操作から復旧できること
- 原本と編集版を取り違えないこと
- 帳票の版が違う・座標が未確定の場合は「判定保留」「安全停止」を正しく見せること
  （使えない帳票を、使えるように見せない）

## 2. 操作の原則

1. **タップ領域は大きく**：通常ボタン最小 48dp、判定入力（○／×／／）は 56dp 以上。
   隣の欄と誤タップしない間隔を取る
2. **片手で完結**：スマホでは主要操作を画面下半分に置く。ページ送り・保存・次へは親指の範囲
3. **屋外で読める**：文字は最小でも本文 14sp 相当、判定記号は大きく太く。
   背景と文字のコントラスト比は 4.5:1 以上を目安にする
4. **触れる欄だけが「入力欄に見える」**：編集可能な欄は枠＋薄い背景色で示す。
   それ以外の帳票部分は紙そのままの見た目にし、ボタンらしく見せない
5. **いつでも戻れる**：入力は自動保存。1つ前の操作の取り消し（元に戻す）を常時表示する
6. **状態は色とラベルで二重に示す**：色だけに頼らない（屋外・色覚差への配慮）

## 3. 状態の見せ方（全体で統一）

文書の状態（作業の進み具合）：

| 状態 | ラベル | 色 |
|---|---|---|
| 編集前 | 原本 | グレー |
| 作業中 | 入力中 | 青 |
| 編集後 | 完了（共有待ち／共有済み） | 緑 |

帳票の判定状態（使えるかどうか）：

| 状態 | ラベル | 扱い |
|---|---|---|
| 利用可 | 利用可 | 入力できる |
| 判定保留 | 判定保留 | 理由を表示し、入力は開かない |
| 安全停止 | 停止中 | 理由と復旧の見通しを表示し、入力は開かない |

帳票カード・一覧・詳細で、このラベルと色を常に同じ位置（左上にバッジ）に出す。

## 4. 画面構成

### 現場アプリ（スマホ／タブレット／iPad）

| # | 画面 | 役割 |
|---|---|---|
| S1 | 物件一覧 | 今日の点検先を選ぶ。検索は物件名・住所。カードに文書の状態バッジ |
| S2 | 帳票一覧 | 物件に紐づく点検票の一覧。帳票ごとに判定状態バッジ。判定保留・停止中は理由を1行で |
| S3 | 点検入力 | 本丸。帳票ページを表示し、定義された欄だけを入力欄として重ねる（§5） |
| S4 | 確認プレビュー | 出力されるPDFの見た目を確認。変更した欄をハイライトし、原本と並べて比べられる |
| S5 | 共有・保存 | 記入済みPDFをクラウドへ共有。原本／編集版のどちらを送るかを最終確認する |

### 社内（タブレット／iPad／PC想定）

| # | 画面 | 役割 |
|---|---|---|
| S6 | 整理・製本 | 物件名・日付・設備種別で絞り込み、最終確認チェックを経て製本・保管へ |
| S7 | 様式準備 | 既存PDFの取り込み、識別値・寸法・ページ構成の確認、記入欄（JSON）定義の確認と承認。判定保留になった帳票の行き先 |

遷移の基本形： S1 → S2 → S3 → S4 → S5（現場の1件分はこの直線で終わらせる）。
S6・S7 は現場フローと混ぜず、入り口を分ける。

## 5. 点検入力画面（S3）の設計

- 帳票は原本の見た目のまま全画面表示し、入力欄だけを重ねる（別の入力フォームに転記させない）
- 欄の種類ごとに部品を固定する：
  - 判定（○／×／／）： 3つの大きなセグメントボタン。選択中は色＋太枠＋記号の拡大で示す
  - 数値： 大きなテンキーシートを下から出す。単位は欄の定義から表示し、範囲外はその場で警告する
  - 文字： キーボード＋定型文候補（前回値・よく使う記入）を上部に並べ、選ぶだけでも進めるようにする
- ページ送りは下部固定バー（前へ／次へ＋ページ番号＋未入力の残り件数）
- 未入力の欄は薄く縁取り、入力済みは落ち着いた色に変える。一覧に戻らなくても進み具合が分かる
- 連動ルールで欄の意味や必須が変わる場合は、変わった欄に理由を1行添える
  （例：「× のため備考が必須」）
- 画面を離れても自動保存され、再開時は「前回の続き」として同じページ・同じ欄から再開する

## 6. 端末別の方針

| 端末 | レイアウト | 主な使い方 |
|---|---|---|
| スマートフォン | 縦・1カラム。主要操作は下部固定 | 片手操作。判定入力とページ送りを優先し、確認プレビューは全画面切替 |
| タブレット | 横・2ペイン（左：帳票ページ／右：欄の一覧と入力） | 立て掛けて両手またはペン。欄一覧から該当箇所へジャンプできる |
| iPad | タブレットに準拠 | 大きめの文字と余白。将来的に手書きメモ欄（Apple Pencil）を足せる余地を残す |

## 7. オフラインと復旧

- 現場は圏外があり得るため、入力は端末内で完結し、オンライン復帰時に自動で同期する
- 同期の状態は常時表示する（同期済み／同期待ち／要確認）
- 誤操作・中断からの復旧： 自動保存＋「元に戻す」＋作業履歴（いつ・どの欄を変えたか）

## 8. 未決事項（機能設計側への確認）

1. 記入欄 JSON に含まれる入力形式の種類の一覧（判定・数値・文字のほかに、選択式・日付・写真などがあるか）
2. 連動ルールの表現方法（欄の必須化・値の自動計算・分岐の見せ方をどこまで UI が担うか）
3. 帳票が複数ページにまたがる場合の、ページと設備の対応づけ（1設備＝複数ページの扱い）
4. 利用者の識別（点検者の切替・記録の要否）と端末の認証方式
5. 写真の添付が点検フローに必要か（必要なら撮影→帳票への紐づけの操作を別途設計する）
6. 社内側（S6・S7）を使う端末と人数（PC前提か、タブレット併用か）

決まったものから v2 以降に反映する。
