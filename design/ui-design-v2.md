# yEgo 操作設計 v2（もち）

作成： 2026-11-11
根拠： プロジェクト計画書（2026-11-11）、操作設計 v1、円卓 議題1 の合意案、
実帳票サンプル 50物件・247ファイルの様式分析（もち、2026-11-11。集計の詳細は
円卓 議題2 に記載）、および事業側（ユーザー）の要件確定（2026-11-11）。
担当範囲は v1 と同じ（アプリデザイン、スマホ／タブレット／iPad の操作設計）。

## v1 からの変更点（要点）

1. **成果物の前提を明確化**：成果物は「原本に文字を重ねた PDF」ではなく、
   帳票定義から**再生成した、入力フィールドを持つ PDF**。S3 の画面表示は
   入力のための表現であり、出力 PDF に画面の見た目を焼き込むものではない
2. **入力の前提が変わった**：点検票の記入欄の大半は前回点検の台帳データで、
   現場で新たに入力するのは**判定・測定値・備考・日付の差分**が中心。
   S3 に「引き継ぎ」の概念と欄の状態（§5）を追加した
3. **様式の2層**を設計に取り込んだ：法定様式（再生成の対象）と社内様式
   （物件管理表・実施確認書・速報版など）。引継ぎ書のように手書きスキャンが
   実態のものは「記録の取り込み」として扱い、再生成の対象と分ける（§4）
4. **備考欄の収まり制御**を入力設計に組み込んだ：欄の容量（文字数・行数）を
   定義側が持ち、入力中に目安と警告を出す（§5）。はみ出し禁止は事業側の
   確定条件であり、プレビューでの確認導線とセットにする
5. **帳票定義は生成元系統ごと**（Print To PDF 系／業務システム生成系で
   ページ寸法に微差がある）。S2・S7 で系統と版を区別して見せる（§4・§7）

v1 の操作原則（大きなタップ領域、片手完結、屋外可読、自動保存と復旧、
状態の二重表示）、状態バッジの体系、端末別方針、オフライン方針は、
変更のない限り v2 でもそのまま有効とする。

## 1. 確定した要件（事業側、2026-11-11）

- 目的は、現在使っている PDF データを分析し、**書き込み可能な PDF データに
  作り変える**こと
- 原本への**重ね描き（オーバーレイ）は採らない**（入力文字が欄の幅・高さから
  はみ出す恐れがあるため）
- 書式は**規定で定められた様式**であり、作り変えで崩れたりズレたりするのは
  論外。罫線・欄の位置・大きさまで原本と一致することが合格条件
- 編集感覚の理想は **Adobe Acrobat で開いてそのまま編集する感覚**
  （書式そのものを開き、欄を押してそのまま書ける）。ただし Acrobat そのものに
  依存する形にはしない。成果物 PDF は標準のフォームフィールドを持ち、
  一般の PDF ツールでも入力でき、yEgo の入力画面がその感覚を現場向けに
  最適化して提供する（事業側、2026-11-11 追加）

## 2. 様式分析からの設計根拠（実帳票 247ファイル・1,842ページ）

- 用紙は A4縦が中心。罫線はベクタ座標として抽出可能で、帳票定義化の土台になる
- 法定様式パッケージの構成：別記様式第1（表紙）／別記様式第3（点検者一覧）／
  設備別点検票／機器管理票・記録表。判定の記入規則は**良好＝○、不良＝×**、
  該当なし等は ／、少数 △
- 入力形式6種（記号／数値／文字／日付／選択式／固定・自動）の実在を確認。
  中心は記号（判定）と文字（備考）。台帳系の数値・文字列は入力ではなく
  引き継ぎデータ
- テキスト層のない PDF（48件）はスキャン＝主に手書きの運用書類

## 3. 操作の原則（v1 から追加分）

7. **入力は差分に集中させる**：引き継がれた値は「確認するだけ」で進める形にし、
   点検者の手間を判定・測定値・備考・日付に寄せる
8. **はみ出しは入力中に防ぐ**：容量のある欄（備考など）は、入力中に残りの
   目安を示し、超えそうならその場で知らせる。保存できてから気づく形にしない
9. **原本と再生成結果を間違えさせない**：文書の状態バッジ（原本／入力中／完了）
   に加え、プレビューでは「規定書式との一致確認」の見比べを必須の経路にする

## 4. 画面構成の変更

前提として、帳票定義は「型」と「物件」の2層で考える（事業側のイメージ、
2026-11-11）：

- **型**：設備ごとに作り上げる帳票定義（規定様式のレイアウト＋記入欄）。
  様式第1（表紙）・様式第3（点検者一覧）は全物件共通の型とする
- **物件**：その物件が持つ設備の型を引き出し、物件の台帳データ（設置場所・
  型式・製造番号など）を反映して、その物件の報告書パッケージを組み立てる
- 台帳系の型（管理票・記録表）は、様式そのものは変えず、物件ごとの機器の
  総数に応じて**シートの枚数だけが増える**。繰り返しの単位はシート全体で、
  各シートの右上に **（1/2）の形式で「何枚中の何枚目か」**を表示する
  （総枚数は物件データの総数から再生成時に決まる。事業側、2026-11-11）
- **様式第1をパッケージの目次にする**：様式第1にはその物件の設備の種類が
  載る。その各設備の行から、対応する設備の点検様式の先頭ページへ
  **PDF内部リンク**を付ける（事業側、2026-11-11）。リンク先は物件の設備
  構成と組み立て後のページ順から再生成時に決まる。アプリ側でも同じ
  関係を S2 の一覧・S3 の移動に使う

画面の骨格（S1〜S7）と遷移は v1 のまま。次を変更する。

- **S2 帳票一覧**：各帳票に様式の種別を出す（法定様式／社内様式／記録）。
  あわせて帳票定義の系統・版を小さく併記し、版違いを取り違えないようにする。
  「記録」（引継ぎ書・写真など）は入力ではなく取り込みの導線に分ける
- **S3 点検入力**：§5 の通り全面改訂
- **S4 確認プレビュー**：再生成された PDF そのものを表示する（成果物の確認）。
  変更した欄のハイライトに加え、原本と並べる/切り替える**一致確認ビュー**を
  用意し、罫線・欄位置のズレがないか目視で確かめる経路を必須にする
- **S7 様式準備**：取り込み時に生成元系統（Print To PDF 系／システム生成系）を
  識別して帳票定義を系統ごとに管理する。備考欄などの容量（文字数・行数・
  フォントサイズ）の定義もここで確認・承認する

## 5. 点検入力画面（S3）の改訂

- 帳票ページを表示し、帳票定義のフィールドだけを入力対象として示す（v1 継続）。
  ただし入力先は画面の絵ではなく**帳票定義のフィールド**であり、出力は
  そのフィールドを持つ再生成 PDF になる
- **欄の状態**を新設し、色とラベルで示す：
  - 未入力（差分対象でまだ入っていない）
  - 引き継ぎ（前回データ・台帳から来た値。未確認）
  - 確認済み（引き継ぎ値を点検者が見て承認した）
  - 入力済み／変更済み（今回入力した、または引き継ぎ値を直した）
  進捗の残り件数は「未入力＋未確認」の数で数える
- 欄の種類ごとの部品は v1 を土台に、次の通り確定する（様式分析で裏付け）：
  - 判定（○／×／／、少数 △）：大きなセグメントボタン。帳票定義が許容する
    記号だけを出す（△ を持たない様式では出さない）
  - チェック（実施確認書の ✔／／）：判定部品と同系統の大きなタップ部品
  - 数値：テンキー＋単位＋範囲警告（v1 継続）。測定値のみ対象で、台帳の
    数値（型式・容量・製造番号）は引き継ぎ表示で入力対象にしない
  - 文字：キーボード＋定型文候補（不良内容と改善指示は定型文の組み合わせが
    多い）。**容量ゲージ**（定義された文字数・行数の目安と残量）を入力欄の
    近くに常時表示し、超過時はその場で警告する
  - 日付：年月日／年月の両形式に対応する日付部品（資格の交付年月日、
    製造年月、点検日など様式ごとに形式が違うため定義に従う）
  - 選択式：用途（項区分）・設備種類・資格種別など、定義の語彙から選ぶ
  - 写真：不良写真の様式に対応し、撮影→コマ（NO.／設備名／所見）への
    紐づけを行う。PDF の記入欄には描かず、様式の版が変わっても自動で
    付け替えない（議題1 の合意案どおり）
- 連動ルール（× のため備考が必須、など）は v1 の通り理由を1行添える

## 6. 社内様式と記録の扱い

- 物件管理表・実施確認書・速報版は、法定様式と同じ「定義→入力→再生成」の
  扱いを基本とするが、規定様式ではないため一致の合格条件は法定様式より
  緩い（ただし見た目の同一性は保つ）。最終的な対象範囲は円卓 議題2 で確認中
- 引継ぎ書（手書きスキャンが実態）と現場写真は「記録」として物件に紐づけて
  取り込み、帳票定義の対象にしない

## 7. 未決事項（円卓 議題2 で扱う）

1. 再生成の一致検証の方法と合格条件の具体化（座標の許容誤差、自動照合の可否）
2. 帳票定義の系統識別値（生成元を何で識別し、版管理とどう組み合わせるか）
3. 台帳データの置き場所と引き継ぎ方法（機能設計の L2／L3 との対応）
4. 備考欄の容量を帳票定義のどの属性で持つか（文字数／行数／フォントサイズ）
5. 社内様式を再生成の対象に含める範囲
6. 議題1 から継続の未決（写真の初期リリース採否、端末の共有/個人と認証、
   社内側の台数・同時人数と S7 の承認者）
