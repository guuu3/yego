# 議題1：操作設計 v1 の未決事項6点

状態：進行中（ラウンド1）
提案者：もち（2026-11-11）
背景：操作設計 v1（design/ui-design-v1.md）の確定には、機能設計側の判断が
必要な点が6つ残っている。ここで三者の意見をそろえ、v2 に反映する。

## 質問と各者の意見

### Q1. 記入欄 JSON に含まれる入力形式の種類は？

判定・数値・文字のほかに、選択式・日付・写真などがあるか。

- もち：部品は「判定／数値／文字／選択式／日付」を標準セットとして設計してある。
  写真や手書きが入ると部品の追加が要るので、種類の一覧は早い段階で確定したい。
- Claude Code：（未記入）
- Codex：入力形式は UI の標準部品から確定せず、帳票・版・欄ごとの定義を根拠に確定することを提案する。
  根拠：`docs/gate-b/02-design-docs-outline.md` の D4 は記号に「○ × ／ △」と横長の楕円を挙げ、
  D5 は数値・日付・記号の型確認を予定している。一方、`design/ui-design-v1.md` §5 の判定部品は
  「○／×／／」の3択なので、△などが必要な欄を表現できない恐れがある。D4 で型・許容値・単位・
  桁数／範囲・空欄の意味を欄ごとに示し、UI と PDF 出力を対応させたい。未入力と「／」は区別する。
  確認条件案：採用対象の全欄が対応表に載り、未知の型・未確定座標では入力を開かず理由を示すこと。
  写真は D1・D6 の保存対象案にあるが、PDF の記入欄の型と同一とは未確定（Q5 で扱う）。
  なお基準計画書 PDF・実際の欄 JSON はこのチェックアウトに無く、ここでの指摘は設計資料の照合であり、
  実装の独立実行による合格判定ではない。

### Q2. 連動ルールの表現はどこまで UI が担うか？

欄の必須化・値の自動計算・分岐など。

- もち：UI は「理由の表示」までを担うのがよい（例：必須になった欄に
  「× のため備考が必須」と1行添える）。計算と判定そのものは機能側に置く。
- Claude Code：（未記入）
- Codex：計算・必須判定は機能側、UI は結果と理由を表示する分担を支持する。ただし理由の表示だけでは
  不十分で、元の値を変更・取り消した場合の再計算、入力済みの従属欄の扱い、未確定・矛盾・循環時の
  停止条件まで規則として定義したい。根拠：`design/ui-design-v1.md` §5 の連動表示・自動保存と
  §7 のオフライン同期、`docs/gate-b/02-design-docs-outline.md` D4 の版管理、D9 の必須欄検査。
  確認条件案：同じ規則の版と入力なら、圏外・再開・同期後・出力時で同じ判定になること。
  「×→備考必須→○へ変更→元に戻す」を例に、理由表示と保存値が一致し、既存入力が黙って消えず、
  必須欄が未解決のまま完了・共有に進まないことを確認する。これは試験条件の提案で、実施済みではない。

### Q3. 複数ページにまたがる帳票で、ページと設備はどう対応づくか？

1設備＝複数ページの扱い。

- もち：現場では設備単位で進み具合が見える方が迷わない。「設備ごとのまとまり」
  でページをまたげる表示を推奨する。
- Claude Code：（未記入）
- Codex：設備単位の表示は妥当だが、ページ順だけから設備を推定しない対応表が必要と考える。
  根拠：`docs/gate-b/02-design-docs-outline.md` D2 の版・繰り返し行、D5 のページごとの識別、
  D6 の設備の識別、D8 の製本順と例外。物件・点検回・設備 ID・帳票の版・ページ・欄 ID の関係を
  明示し、同種設備が複数ある場合や、1ページに複数設備が載る場合も確認対象にしたい。
  確認条件案：1設備が複数ページにまたがる例、ページの欠落・重複・並べ替え・版混在の例で、
  入力先と再開位置を取り違えず、不明な対応は保留にすること。`design/ui-design-v1.md` §5 の
  未入力件数は、対象設備・必須欄・対象外欄の数え方を決め、単なるページ閲覧を完了と数えない。

### Q4. 利用者の識別（点検者の切替・記録）は必要か？

- もち：報告書に点検者名が要るなら記録は必須になる。UI 側は開始時に
  1タップで選べる軽い切替にしたい。認証方式の希望もあわせて知りたい。
- Claude Code：（未記入）
- Codex：点検者名の選択と、本人確認・権限の確認は分けて定義したい。1タップの切替だけで本人の操作と
  証明できるとは扱わない。根拠：`design/ui-design-v1.md` §7 の作業履歴・オフライン復旧と、
  `docs/gate-b/02-design-docs-outline.md` D2 の承認記録、D8 の点検者一覧。
  記録案は操作者 ID、対象の点検・欄、変更前後の値、操作日時、同期状態。点検者として報告書に載る人と
  代理入力した人を区別し、S7 の承認者が誰かも明示したい。認証方式は共有端末の有無・圏外利用・
  点検者切替時の確認方法を事業側に確認してから決める。
  確認条件案：圏外で A→B に交代し再開・同期しても A の記録が B に付け替わらず、
  権限のない利用者がテンプレートを承認できないこと。個人情報の保存範囲・保持期間も未決として残す。

### Q5. 写真の添付は点検フローに必要か？

- もち：現場では撮影の需要が高いと予想する。入れるなら「記入欄に紐づく写真」
  として設計したい（帳票と別管理にしない）。要否の早期決定を希望。
- Claude Code：（未記入）
- Codex：写真は単なる新規要望ではなく、`docs/gate-b/02-design-docs-outline.md` D1 の L3 と
  D6 の保存対象案に既にある。ただし初期提供で必須か、何枚・どこへ出力するかは未確定なので、
  事業側に採用範囲を決めてもらいたい。採用するなら物件・点検回・設備・指摘事項に紐づけ、
  必要に応じて欄 ID まで保持する。版更新で欄の対応が不明になっても、別欄へ自動で付け替えない。
  根拠：同 D6 の版保持と `design/ui-design-v1.md` §7 の端末内保存・同期。
  確認条件案：圏外撮影、中断、再送、削除の各操作で欠落・二重登録・別物件への混入が起きず、
  未同期・失敗を画面で把握できること。PDFへの掲載方法、容量上限、保存先・保持期間・閲覧権限も
  決定が必要。写真の実データを Git に置かない点は `AGENTS.md` と D9 の制約に従う。

### Q6. 社内側（S6・S7）を使う端末と人数は？

PC 前提か、タブレット併用か。

- もち：端末が決まれば画面の情報密度を決められる。PC 前提なら一覧性を優先し、
  タブレット併用なら現場側と操作をそろえる。
- Claude Code：（未記入）
- Codex：`design/ui-design-v1.md` §4 は社内側を「タブレット／iPad／PC想定」、§6 は端末別配置を
  示すが、利用台数・同時利用人数の根拠はないため、PC 専用とは確定できない。
  S6 の整理・比較と S7 の座標確認・承認は別作業として、主端末、最小画面、入力方法、同時編集者数を
  事業側に確認したい。暫定案は PC を主な検証端末とし、タブレットで必要な操作は別途確認する。
  根拠：`docs/gate-b/02-design-docs-outline.md` D2 の承認状態、D8 の出力の版管理と、
  `design/ui-design-v1.md` §1 の原本・編集版の取り違え防止。
  確認条件案：採用する端末ごとに版・状態・対象ページを識別でき、原本と編集版を誤らず比較・共有できること。
  2人が同じ対象を更新・承認する場合も、古い内容による上書きや未確認版の承認を防ぐこと。
  実端末での操作試験は未実施であり、端末対応済みという判定はしない。
