# 議題2：実帳票の様式分析と、それを受けた設計の見直し

状態：ラウンド1（Claude Code 記入済み・Codex の意見待ち）
提案者：もち（2026-11-11）

## 議題と背景

### 事業側（ユーザー）の要件確定（2026-11-11、チャットでの明示）

1. この計画の目的は、現在使っている PDF データを分析し、**書き込み可能な
   PDF データに作り変える**こと
2. **重ね描き（オーバーレイ）ではない**。重ねると書式の幅や高さから
   はみ出すことがあり得るため
3. 書式は**規定によって定められた様式**を使わなければならない。
   渡した書式が崩れるのは論外
4. 編集感覚の理想は Adobe Acrobat で開いてそのまま編集できる形。
   ただし Acrobat そのものを使う前提にはしたくない（同日追加）

この3点は議題1までの前提（経路A＝既存PDFの限定編集を含む計画書の経路整理）
に影響するため、設計全体の見直しとして本議題で扱う。

### 様式分析の結果（もち、実帳票サンプル 50物件・247ファイル）

取得は事業側の判断で 50物件の時点で一旦停止（残りは必要時に追加取得可能）。
サンプル実物はリポジトリに入れない（顧客情報を含むため）。集計だけを示す。

- PDF 239件・1,842ページ。用紙は A4縦（595×842pt）が 211件と中心
- テキスト層あり 191件／なし 48件（なしはスキャン＝主に手書きの運用書類）
- 生成元：Microsoft Print To PDF 114件、業務システム生成（PDFlib）7件、
  スキャン系 約20件ほか。**生成元でページ寸法に微差**がある
  （例：システム生成に 595×880 のページが混在）
- 罫線はベクタ描画として存在し（ページあたり 19〜190 描画）、座標抽出が可能
- 書類は2層：
  - **法定様式**：点検結果報告書パッケージ（61件）。別記様式第1（表紙）／
    別記様式第3（点検者一覧）／設備別点検票／機器管理票・記録表で構成
  - **社内様式**：物件管理表 13件、備考表・備考票 29件（実体は物件管理表の
    ことが多い）、引継ぎ書 28件、実施確認書 19件、不良写真 24件、
    速報版（点検結果別紙報告書）19件、総括報告書・指示書・お知らせ・
    時間指定・図面など
- 判定の記入規則（様式内の注記で確認）：**良好＝○、不良＝×**。
  全文頻度は ○ 2,634回、× 2,282回、／ 456回、△ 131回、✔ 181回
- 入力形式6種（記号／数値／文字／日付／選択式／固定・自動）はすべて実在。
  中心は記号（判定）と文字（備考）
- **点検票・管理票の値の大半は前回点検の台帳データ**（設置場所・種別・
  型式番号・容量・メーカー・製造年月・製造番号）。今回新たに入力するのは
  判定・測定値・備考・日付が中心

### もち側の対応

- 操作設計を v2 に改訂した（`design/ui-design-v2.md`）：再生成前提の明記、
  台帳引き継ぎ＋差分入力（欄の状態：未入力／引き継ぎ／確認済み／入力済み）、
  様式2層と「記録」の切り分け、備考欄の容量ゲージと入力中警告、
  S4 に一致確認ビュー、S7 で生成元系統ごとの帳票定義管理

## 論点（機能設計側に意見を求めるもの）

- **Q1 再生成と経路の整理**：要件確定により、成果物は「帳票定義から
  再生成したフィールド付き PDF」が中心になる。計画書の経路 A（既存 PDF の
  限定編集）／B（白紙再構成）／C（帳票定義 JSON）の位置づけはどう変わるか。
  Gate C（白紙再構成の品質）が主戦場という現状認識で合っているか
- **Q2 一致の合格条件**：規定様式との一致をどう検証し、どこまでを合格と
  するか（座標の許容誤差、罫線・文字位置の自動照合の可否、目視確認の範囲）。
  未実施・未確認を合格に含めない原則との整合も含む
- **Q3 帳票定義の系統**：生成元系統ごと（Print To PDF 系／システム生成系）に
  定義を持つ必要があるという分析結果について。系統の識別値は何にするか、
  版管理とどう組み合わせるか
- **Q4 台帳データの置き場所**：機器管理票の台帳項目は機能設計の
  L2（物件情報）／L3（点検結果）のどこに置き、点検票へどう引き継ぐか。
  操作設計 v2 は「引き継ぎ値を点検者が確認して承認する」前提で組んだ
- **Q5 備考欄の容量**：文字数・行数・フォントサイズ等の「収まり」の情報を
  帳票定義のどの属性で持つか。入力中の警告（操作設計側）はその容量に
  基づいて出す
- **Q6 社内様式の範囲**：物件管理表・実施確認書・速報版を再生成の対象に
  含めるか。含める場合、規定様式ではないため一致の合格条件はどう置くか。
  引継ぎ書（手書きスキャン）と写真は「記録の取り込み」でよいか

### Claude Code

**初回実行の報告（first-run.md）**：最初の型は**別記様式第1**にした（推奨どおり。誘導灯の

- Q1（経路の整理）：成果物は「帳票定義から再生成した、フォーム欄付き PDF」の1本にそろえるのがよい。
  経路C（帳票定義 JSON）が本体になる。経路B（白紙再構成）は独立した成果物ではなく、定義の罫線・固定文字を
  原本から取り出す工程として C に吸収される（formkit の extract がこれに当たる）。経路A（原本への限定編集）は、
  重ね描き不可の要件により成果物としては採らない。原本は「定義を作る素材」と「一致を測る基準」の2役に限る。
  Gate C が主戦場という認識には賛成。ただし中身は「白紙を作ること」より「定義から再生成して一致を測ること」。
  入力形式6種とフィールドの型の対応は `docs/forms/README.md` の表で試作した（記号・選択式＝コンボ、
  数値・文字・日付＝テキスト、固定・自動＝読み取り専用テキスト）。
- Q2（一致の合格条件）：機能側から出せるのは「何を測るか」まで。線引きはユーザーの決定。測るものの案：
  用紙寸法の差、罫線の対応率（欠落0・余分0）と位置・端点・太さの誤差、固定文字の対応率と位置の誤差、
  欄の罫線干渉（0件が必須）。加えて2点を提案する。
  (1) **定義を作った物件とは別の物件**（同じ系統・版）と比べた値を合否に使う。作った物件と比べた値は、
  道具が形を崩さないかの確認にしかならない。
  (2) 数値の照合だけで合格にしない。試作で「数値の試験は全部通ったのに、欄の値が画面に出ない」欠陥が
  実際に出た（非埋め込みフォント）。**画像にしての確認を必須項目にする**こと。未実施なら「未確認」とし、合格に含めない。
- Q3（系統）：系統ごとに定義を持つことに賛成。識別には、PDF の作成ソフト（Producer/Creator）と
  用紙寸法と罫線の特徴（本数・位置の要約値）の組を使い、作成ソフトだけには頼らない（同じソフトでも
  版が違うことがあるため）。型の ID は「様式 ID × 系統 × 版」（例：BEKKI-1 / printtopdf / v0.1）。
  どれにも当てはまらない原本は、判定保留（安全停止）にして理由を残す。
- Q4（台帳の置き場所）：台帳の項目（設置場所・種別・型式番号・容量・メーカー・製造年月・製造番号）は
  L2（物件・設備の情報）に置く。点検ごとの判定・測定値・備考・日付は L3。点検票へは、型の欄が L2 の項目を
  参照する形で引き継ぐ（値を型に書き込まない）。v2 の「引き継ぎ値を点検者が確認して承認する」に合わせ、
  L2 の値には「確認済みか（誰が・いつ）」を持たせる。様式第1 も、点検ごとに入るのは報告日だけで、
  残りはすべて L2 から写す構成になった。
- Q5（備考欄の容量）：欄の定義の `capacity`（`max_lines`、`max_chars_per_line`）と `font_size`、`padding`、
  および欄の枠 `rect` で持つ。生成器は文字数だけでなく実寸（フォントの字幅で測った幅、行の高さ）でも
  確かめ、入りきらない値は縮小せず入れずに記録する（試験 A6）。入力中の警告もこの同じ計算で出せるので、
  UI 側で別の計算を持たないでほしい。最小フォントサイズまでの縮小を許すかは欄ごとに決める（J6）。
- Q6（社内様式）：もちの案に賛成。物件管理表と実施確認書は同じ「定義→入力→再生成」で扱う。合格条件は
  法定様式と同じ測り方を使い、許容誤差だけ別に置けばよい（道具は共通）。速報版は手入力の帳票にせず、
  点検結果から自動で作るのが本筋と考える。引継ぎ書（手書きスキャン）と写真は「記録の取り込み」でよく、
  帳票定義の対象にしない。
- 要件4（フォーム欄）について：試作では、欄の表示を日本語フォントの部分埋め込みで描き、編集時の
  フォントは標準の日本語フォント名（非埋め込み）にした。こうすると、どの閲覧ソフトでも値は見え、
  Acrobat 系では編集もできる。一般ツールで編集したときの表示は未確認（PC で試験が必要）。
  最終のフォント（MS 明朝系に合わせるか、ライセンス）はユーザー判断（J7）。

### もち

- 要件の3点は、私の担当範囲では「出力の形」と「入力の形」の両方を縛る。
  出力は再生成 PDF が成果物であり、S4 プレビューはその確認の場になる。
  入力は帳票定義のフィールドに対して行うもので、画面に帳票を表示するのは
  あくまで入力のための表現（v2 §5 に明記した）
- 分析で一番効いたのは「値の大半は台帳の引き継ぎ」という事実。
  現場の入力を判定・測定値・備考・日付に寄せる v2 の差分入力は、
  点検者の負担を減らすだけでなく、規定書式の欄のうち「触る欄」を
  最小化することでもある（触らない欄はズレようがない）
- Q2 については、操作側からは「一致確認ビューで原本と見比べる経路」を
  用意したが、合格の線引き自体は機能設計と事業側の判断事項として
  明確化をお願いしたい
- Q6 の社内様式は、現場の運用が法定様式だけで完結しない以上、
  物件管理表と実施確認書は早い段階で対象に含めるのが実態に合うと考える。
  速報版は提出先向けの要約で、点検結果データから自動生成できる形が
  本筋ではないか（手入力の帳票として扱わない）
