## 1. 方式と材料

- 座標源（物件A）とホールドアウト（物件B、座標決定には未使用の別物件）の2物件で照合した（様式第1 と同じホールドアウト方式）
- どちらも配置A（多数派）。その型のサンプル全件（点検票 55 件・管理票 61 件）で枠位置の分布を取り、系統を分けた（§4）
- 原本の「○」印はベクタの円、「／」印はベクタの斜線で描かれている。formkit の extract は斜線を水平・垂直の
  セグメントに分解して罫線に混ぜるため、原本側の線の集計では斜線を分離して真の罫線だけで数え直した。
  measure の「原本にあり再生成に無い」線は、明細と斜線リストを照合して内訳を切り分けた（§2 の各表）
- 再生成は定義 v0.2＋匿名ダミーデータ（`forms/data/test/*.dummy.json`）。生成できた欄は
  KOKUJI-01-1 が 181、KOKUJI-01-2 が 214、SHOKAKI-KANRI が 386（いずれも全欄）
- 明細 CSV の同梱は §4-6（text 列が固定文字だけ）で判断した。KOKUJI-01-1 と SHOKAKI-KANRI は条件を満たすため
  同梱する。KOKUJI-01-2 は器種別集計表の記入（器種名・数）が text 列に入るため同梱せず、要約 JSON のみとする

## 3. バトン「確かめること」4点の結果

1. **点検票の「／」の運用**（Print To PDF 系 51 ページで集計）
   - その1（19 項目×51）：種別セルは ○ 979・／ 538・空欄 4,290。行の内訳は「設置種別すべて ○ → 判定 ○」623 行、
     「すべて ／ → 判定 ／」340 行、「○ と ／ の混在 → 判定 ○」2 行、不良個数の記入 3 行
   - その2（21 項目×51）：種別セルは ○ 80・／ 2,041・空欄 4,294。判定は ／ 1,005 行・○ 59 行・不良個数 7 行
     （大半の物件は機器点検のみで、内部等・機能の行は全行 ／ になる）
   - 解釈：／ は「その種別は設置されているが、その項目は該当しない」。設置されていない種別のセルは空欄のまま。
     判定は「設置種別の少なくとも 1 つが ○ なら ○、すべて ／ なら ／、不良があれば不良個数」
   - 定義への反映：種別欄の `allowed` に「／」を追加し（v0.1 は ○ のみだった）、判定欄の note に運用を記録した
2. **管理票の行数と「機能 年月日」**
   - 1 シートは **35 行**（行高 18.0pt、最下行のみ 19.44pt）。v0.1 の仮 10 行は誤りで、定義を 35 行に拡張した
     （欄 111 → 386、ルールも 35 行分）。35 行すべてを使うシートも 61 ページ中 6 件ある
   - 「機能 年月日」は **1 列**（見出しが「機能／年月日」の 2 段表記）。記入は機能点検を実施した行だけで少数
     （多数派系統 53 ページで 15 行）、書式は「YYYY.M」（西暦＋月。例：2026.5）
   - 製造年月は年のみ（西暦 4 桁）の記入が多数。管理票の判定は ○ 693・× 37・空欄 6・／ 1（61 ページ・記入 737 行）
3. **その2 の頭の部分**：**無い**。その2 は表題（別記様式第1／消火器具（その2））の直下から点検表が始まり、
   名称・点検年月日などの頭部ブロックは存在しない（全 55 件で確認）。v0.1 の open_questions の 1 件目はこれで解決
4. **枚数欄の有無**：管理票 61 ページすべてで（i/n）形式や「枚」の表示は**無い**。原本に枚数欄は存在しない。
   定義の `sheet_counter` は未確定のまま（付ける位置は生成側の決定事項）

## 6. 申し送り・残課題

1. **その2 の器種別集計表に欄が無い**（欄構成の不足。機能設計側の領分）：測定機器表の下に
   「器種名／設置数／点検数／合格数／要修理数／廃棄数」の表（データ 6 行）が全 55 件にあるが、v0.1 の欄構成に無い。
   幾何は実測済み：表の範囲 x 36.48..532.92、見出し行 y 258.24..276.60、データ行 y 147.00..258.24（行高 ≒18.36pt×6）。
   列は器種名 36.48..176.52、設置数 176.52..235.56、点検数 235.56..294.60、合格数 294.60..353.64、
   要修理数 353.64..444.00、廃棄数 444.00..532.92。データ行には「＜外観点検＞」「＜機能点検＞」の
   見出し行も混ざる（行の意味づけは欄の設計時に決める）。定義の open_questions にも記録した
2. **KOKUJI-01-1 のホールドアウト 5 字（最大 0.354pt）の扱い**：原本同士のばらつきを 0.00pt 基準で
   どう扱うかの判断が要る（この型を合格にできるか、座標源をどちらの製作分に合わせるか）
3. **配置B・PDFlib 系**：§4 のとおり。B は原点ずらしの方針が決まっているが直接の取り直しは未実施、PDFlib 系は未着手
4. **formkit の堅牢性（Claude Code 側）**：`capacity` の `max_lines` / `max_chars_per_line` が null の定義で
   generate が TypeError になる（v0.1 のその2 備考が該当。v0.2 では実測値 4 行×47 字を入れて回避した。根本対応は未実施）
5. **点検者名の語彙**：KOKUJI-01-1 の `inspector_name` の `allowed` は v0.1 の仮置き
   （「（点検者台帳から。台帳は未作成）」）のままで、ダミー生成でも値が入らなかった。点検者台帳の形が決まれば差し替える
6. **原本の「縮小して入れる」記入と formkit 方針の差**：原本は欄幅を超える値を字を縮小して入れている
   （その2 備考で 9.72pt・9.27pt、管理票のメーカー・製造番号でも縮小を観測）。formkit は縮小せず
   「入りきらない値は入れない」方針のため、長い値の運用が異なる。実害の有無は実データ投入時に確認が要る
