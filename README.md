# yEgo

消防設備点検のPDFを「壊さず編集する」ためのシステム。
現場で入力 → 原本の書式を保持 → PDFを共有 → 社内で報告書を完成させる。

- 既存の公式・社内様式を勝手に変えないことを最優先とする
- 元PDFは読み取り専用の基準として保存し、編集版は新規ファイルとして作る
- 入力できる欄は明示的に定義されたものだけ。座標が確定しない欄は編集禁止
- 開発は品質ゲート方式：前のゲートの必須項目を100%通過したときだけ次へ進む

基準資料： `docs/plan/yego-project-plan-20261111.pdf`（プロジェクト計画書、2026-11-11）
※ PDFなどバイナリはローカルの git から追加する（原本PDF・完全版CSVはこのリポジトリに入れない）。

## 作業分担（2026-11-11 決定）

| 担当 | 担うこと |
|---|---|
| Claude Code | 機能設計、大量PDFの解析、実装、異常試験、結果CSVとPDF、Git履歴とバックアップ |
| Codex (ChatGPT) | 報告内容の独立レビュー、要件・合格条件の整理、設計の抜け・リスク指摘、計画書・意思決定資料 |
| もち | アプリデザイン、スマートフォン／タブレット／iPad の操作設計とデザイン（`design/`） |
| 事業側の承認者 | 白紙の定義、帳票の採用範囲、実運用の判断、リスクの受け入れ可否 |

## フォルダ

- `docs/` — 計画書・機能設計書（Claude Code / Codex の成果物）
- `design/` — 画面設計・操作設計（もちの成果物）
- `roundtable/` — 三者が意見を出し合う円卓（進め方は roundtable/README.md）
- 実装コードは決まり次第ここに追加する

## 進め方

1. 機能設計が `docs/` に入る → もちがそれを読んで `design/` に画面・操作設計を置く
2. 実装は `design/` の操作設計に沿って行い、食い違いが出たら設計側へ差し戻す
3. 決めきれないことは円卓（`roundtable/`）で三者の意見をそろえ、ユーザーが決定する
4. 判定は計画書の定義どおり：未実施・未確認・不合格を「合格」に含めない
