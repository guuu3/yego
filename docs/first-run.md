# 初回実行の指示書（Claude Code へ）

yego のセッションを初めて本格稼働させるときの実行指示。
対象リポジトリは **guuu3/yego のみ**（クラウドセッションでは開始時に
このリポジトリだけを選んで新規セッションを作ること）。

## 開始時に必ずやること

1. `roundtable/` を確認し、自分の欄が未記入の議題に意見を書く
   （議題1は合意案提示中、議題2はラウンド1で本書と並行して進めてよい）
2. `design/ui-design-v2.md` を読む。操作設計は v2 が最新版であり、
   実装との食い違いは実装側で勝手に変えず、未決事項として残す

## 確定している要件（事業側、2026-11-11。覆らない前提）

- 目的は、現在使っている PDF データを分析し、**書き込み可能な PDF
  データに作り変える**こと。原本への重ね描き（オーバーレイ）は採らない
- 書式は規定で定められた様式であり、作り変えで崩れるのは論外。
  罫線・欄の位置・大きさまで原本と一致することが合格条件
- 編集感覚の理想は Acrobat で開いてそのまま編集できる形。成果物 PDF は
  標準のフォームフィールドを持ち、Acrobat そのものには依存しない
- 帳票定義は「型×物件」の2層：設備ごとに型を作り上げ、物件ごとに
  必要な型を引き出して物件データ（台帳）を反映する
- 台帳系の型は様式を変えずシートの枚数だけが増え、各シート右上に
  （1/2）形式の枚数表示を付ける
- 様式第1に載る設備の各行から、その設備の点検様式の先頭ページへ
  PDF 内部リンクを付ける

## 初回実行の対象：最初の「型」の試作

推奨は **別記様式第1（点検結果報告書の表紙）**。理由：全物件共通の型で
あること、パッケージの組み立てと設備リンクの起点になること、構造が
比較的単純で再生成の進め方（定義→再生成→一致測定）を確立するのに
向くこと。

ただし Gate C で誘導灯の白紙再構成がすでに進行している場合は、
その線を止めず、そちらを最初の型として本書の進め方を適用してよい。
どちらを選んだかは、円卓 議題2 の自分の欄に明記すること。

### 進め方

1. 対象様式について、実帳票の分析結果（罫線・文字の座標、記入欄の
   位置・種類・大きさ）を帳票定義に落とす。記入欄の入力形式は6種
   （記号／数値／文字／日付／選択式／固定・自動）で分類する
2. 帳票定義から、標準フォームフィールドを持つ PDF を再生成する
   （検証には匿名化したダミーデータを使う）
3. 原本と再生成結果を重ねて見比べ、罫線・欄位置・文字位置の誤差を
   **実測して数値で残す**。この実測が円卓 議題2 Q2（一致の合格条件）の
   判断材料になる
4. 結果（定義・サンプル・実測値・残った課題）をリポジトリに上げ、
   円卓 議題2 の自分の欄に要約とリンクを書く
5. `docs/progress.md`（進捗のバトン）に状態を記録する。以後の
   定常運転（docs/routine.md）はこのバトンを正本として継続する

### 完了の定義

- 帳票定義の初版と再生成サンプルがリポジトリにある
- 一致度の実測値が数値で残っている（目視の「だいたい合っている」は不可）
- 未実施・未確認の項目が合格に紛れていない

## やらないこと・止まる条件

- 原本 PDF・完全版 CSV・顧客情報はリポジトリに入れない。
  検証データは匿名化したものだけを使う
- `design/`（もち担当）は編集しない。設計変更の提案は円卓で出す
- 規定様式との一致が取れないまま次工程（現場UIとの統合など）に
  進まない。一致しない場合は、どこが・どれだけ違うかを記録して止める
- 判定に迷う仕様は推測で決めず、円卓 議題として残す

## 次の型の優先順位（初回の後の目安）

1. 消火器具の点検票＋消火器管理票（最も一般的で、台帳の繰り返しと
   （1/2）表示のパターンを確立できる）
2. 自動火災報知設備の点検票
3. 別記様式第3（点検者一覧表）
4. その他の設備様式、社内様式（物件管理表・実施確認書）
