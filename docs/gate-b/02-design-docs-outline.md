# 02 設計書 9本の構成案

作成日: 2026-11-05 ／ 状態: **案（未承認）**

## 前提

- 既存の設計書は、このセッションでは見つかりませんでした（`01-gate-a-consistency-check.md` の1章）。そのため、この構成案は**既存の設計書との重なりをまだ確かめていません**。既存の設計書を受け取ったら、各設計書の「既存システムとの関係」を書き直します。
- 各設計書の「既存システムとの関係」は、**確かめる項目**として書いています。既存のコードを見ていないため、「〜がある」「〜に使える」とは断定していません。
- 数値の目標（±0.5pt など）は、Gate A 報告書 10章の**検証前の目標値**です。D9 の試験で実測してから決めます。

## D1 全体構成と4階層のデータモデル

- **目的**: 「帳票テンプレート」「物件の情報」「今回の点検結果」「出力」を分けて管理し、どの帳票も同じ流れで扱えるようにする。
- **対象機能**: 最終目標の1〜10すべての土台。
- **4つの階層**:
  1. **L1 共通帳票テンプレート**: 様式・その番号・版・用紙の寸法ごとに作る。白紙の PDF、固定の要素、記入欄の定義を持つ。
  2. **L2 物件別の設備情報**: 物件名・所在・設備の型式・設置数など。前年から引き継ぐ。
  3. **L3 今回の点検結果**: 判定の記号・数値・備考・写真・指摘事項。
  4. **L4 出力**: 消防署提出用・顧客提出用の PDF と製本。作るたびに版を残し、上書きしない。
- **物件管理表の扱い**: 点検票とは別の「帳票ファミリー」とする。L1 にテンプレートを持ち、内容は物件の運用情報（入館方法・連絡先・借用キー）として L2 の横に置く。点検報告書一式の製本には入れない。
- **既存システムとの関係（確かめる項目）**:
  - 今のデータモデルが「設備中心」か「帳票中心」か。
  - 4つの階層に当てはまらないテーブルがあるか。
  - 生成した PDF をどこに、どう保存しているか。
- **技術的な方法（案）**:
  - **テンプレートを作る処理**（解析・復元・検証）は、Gate A の Python の道具を発展させ、オフラインのバッチとして動かす。
  - **アプリの処理**（入力・再記入・製本）は、Next.js・TypeScript・pdf-lib で動かす。
  - 2つの間は、版の番号を付けた JSON（テンプレートの定義）と白紙の PDF だけで受け渡す。
- **検証方法**: 帳票の種類ごとに、L1〜L4 のどこに何を置くかの表を作る。漏れや二重持ちが無いことを、レビューで確かめる。
- **未解決事項**:
  - 解析を Python にするか TypeScript にするか（判断事項 J3）。
  - 顧客の PDF をどこに置くか（判断事項 J8）。
- **実装時の注意**: 原本の PDF は読み取り専用の置き場に置き、ハッシュ値で管理する。すべての出力から原本までたどれるようにする。

## D2 帳票テンプレートの登録と版の管理

- **目的**: Gate A の 450 の版（罫線の一致度 0.93 でまとめたもの）を、そのまま正式なテンプレートにはしない。比べて決めたうえで、正式なテンプレートとして登録する。
- **対象機能**: 最終目標の2・6・7。
- **テンプレートの決め方**:
  1. 版に、様式（第20 など）・その番号を付ける（印刷された見出しの文字から決める）。
  2. 同じ様式・その番号の中で、次の5つを比べる。
     - 用紙の寸法: A4 と 595×880 は**別のテンプレート**（Q3）。
     - 罫線の差: 決まった範囲の中でのずれか、構造の違いか。
     - 固定の文字の差: 「日本工業規格」と「日本産業規格」は**別の版**として持つ（Q4）。
     - 行の数が変わるか: 行の数だけが違うものは、1つのテンプレートの「繰り返す行のまとまり」として扱う。
     - 作成ソフト: Print To PDF か PDFlib か（Q2）。
  3. 結果を、**正式テンプレート ＞ 版の違い ＞ 元の版（Gate A の番号）** の3段で登録する。
- **テンプレートの状態**: `候補` → `復元済み` → `検証済み`（D9 に合格）→ `承認済み`（利用者が確認）→ `使用中`／`廃止`。
  - **A 評価でも、自動では `承認済み` にしない。**
- **既存システムとの関係（確かめる項目）**: 今の PDF 出力で、帳票の定義をどう持っているか（コードに直接書いているか、データか）。
- **技術的な方法（案）**: テンプレートの定義は JSON で、版の番号を付けて Git と Supabase Storage に置く。中身は次のとおり。
  - 寸法・罫線の特徴・固定の文字の一覧
  - 記入欄（D4）
  - 繰り返す行のまとまり
  - 元の版の ID・状態・承認の記録
- **検証方法**: 7,410 ページをすべて、どれか1つの正式テンプレートに当てはめる。当てはまらないページと、2つ以上に当てはまるページを数える。
- **未解決事項**:
  - 罫線の差を、どこまでなら「同じテンプレートの中のずれ」とするか（D9 で実測）。
  - 1物件だけの版（90版・105ページ）の扱い（J5）。
- **実装時の注意**:
  - 1つのテンプレートが、どの物件のどのページに使われているかを残す。
  - テンプレートを直したときに、どこまで影響するかを出せるようにする。

## D3 白紙テンプレートの復元

- **目的**: 記入の無い白紙の PDF を作る。罫線・印刷の文字・フォントは、元のままの**ベクターのデータ**として残す。
- **対象機能**: 最終目標の2・6。
- **方式**: 比べた結果は `03-template-and-restoration-policy.md`。基本は「完成した PDF から、記入の文字・図形を1つずつ取り除く方式」です。
  - 次の方法は、正式な方式にしない: **画像にする**、**白で塗る**。
- **既存システムとの関係**: なし（新しい処理）。
- **技術的な方法（案）**:
  1. 物件を重ねて、固定の文字と記入を分ける（Gate A 5.3）。
  2. 元にする物件を1つ選ぶ。罫線のずれが一番小さく、記入が少ない物件にする。
  3. その物件の PDF の中身（描画の命令の並び）を読み、記入と判定した文字の命令と ○／× の図形の命令だけを取り除く。
  4. 判定できなかった命令は消さず、`要確認` として利用者に見せる。
- **検証方法**:
  - SANKEILOGI戸田の物件別テンプレートと比べる（事前記入を除く）。
  - 1物件を抜いて作る試験をする（D9）。
  - 罫線が欠けていないか、図形の数で確かめる。
- **未解決事項**:
  - SANKEILOGI戸田の ○／ が、点検結果か初期値か（Q5。未確定のまま扱う）。
  - 「機器・総合」の文字が、印刷か記入か（Q8。帳票ごとに分ける）。
- **実装時の注意**:
  - 埋め込みフォントのサブセットに無い字は、白紙の文字としても使えない。白紙を作る処理と、記入に使うフォント（D4・D7）は分けて考える。
  - 本格的な生成は、承認を得てからにする（今回はしない）。

## D4 記入欄・座標・記入規則

- **目的**: AI に毎回位置を決めさせない。実測で決めた規則で記入する。
- **対象機能**: 最終目標の4・6・8。
- **欄ごとに持つ項目**:
  - 欄の ID・意味（どのデータの項目か）
  - 欄の枠（座標）と、使える幅・高さ
  - 揃え（左・中央・右）、基準線
  - フォント・文字の大きさ（標準と最小）、文字の間隔、行の間隔
  - 改行の規則（文字単位・禁則・最大の行数）
  - 入りきらないときの扱い: 縮小 → 改行 → 別紙 → エラー の順。どこまで使うかは欄ごとに決める（J6）。
- **記号の欄に持つ項目**: 選べる記号（○ × ／ △）、列ごとの中心の座標、大きさ、線の太さ（版ごとに実測。Q6）。
  - 報告書の横長の楕円は、別の種類の記号として持つ。
- **規則の決め方**: 欄ごとに、既存の記入を集めて決める。
  - 位置: 位置の分布
  - 文字の大きさ: 一番多い値と幅
  - 改行: 改行していた例
  - 記号: ○ の中心は、列ごとの中央値（Gate A ではばらつきの中央値が 0.0pt）
- **フォント（Q7）**: 字形・文字幅・描画の結果を、候補のフォントと比べて決める。決まらない場合は、候補と不確かさを報告する。
  - 使えるかどうか（ライセンス）も確かめる（J7）。
- **既存システムとの関係（確かめる項目）**: 今の PDF 出力の座標の定義、使っているフォント、日本語の改行の処理。
- **検証方法**: 規則で並べた位置と、元の記入の位置の差を、欄ごとに測る（D9）。
- **未解決事項**:
  - 元のフォントが特定できない場合に、何で代えるか。
  - 古い版の小塚明朝の扱い（Q2）。
- **実装時の注意**: 規則は、テンプレートの版と一緒に版の番号を付けて管理する。手で直した場合は、その記録を残す。

## D5 既存 PDF の取り込みと記入内容の抽出

- **目的**: 完成した PDF から、物件の情報（L2）と点検結果（L3）を取り出し、編集できる形で保存する。
- **対象機能**: 最終目標の1〜3・5・9。
- **流れ**:
  1. PDF を読み込む。ハッシュ値を記録し、原本は変えない。
  2. ページごとに正式テンプレートを決める（D2）。
  3. 罫線で位置を合わせる。
  4. 文字・図形を欄に割り当てる。
  5. 割り当てた値の型を確かめる（数値・日付・記号）。
  6. 確かさが低いものは `要確認` に回す。
- **L2 と L3 の分け方**: 同じ物件の2回分以上（前回と過去のデータ）を比べて、欄ごとに「物件ごとに同じ」か「毎回変わる」かの傾向を決める（Gate A 4章）。2回分が無い物件では、欄の既定の区分を使う。
- **対象外**:
  - 画像だけのページ（押印版・スキャン版の 97件）の文字の読み取り（OCR）は、初期の開発では行わない。製本では、画像のページとしてそのまま差し込む。
  - 赤字の手書きの読み取り（Q9）。
- **既存システムとの関係（確かめる項目）**: 今、PDF を取り込む機能があるか、写真や設備のデータとどうつなぐか。
- **検証方法**:
  - 評価用の 50 物件で、取り出した値と、目で見て作った正解を比べる。
  - 欄の正解率と、`要確認` になった割合を測る。
- **未解決事項**:
  - 1つの欄に入りきらず隣の欄にはみ出している記入の扱い。
  - 2つの版が混ざっている物件の扱い（Gate A 5.1）。
- **実装時の注意**: 判定できないものを推測で埋めない。すべての値に「どの PDF の、どのページの、どの命令から取ったか」を残す。

## D6 物件・設備・点検結果のデータと前年からの引き継ぎ

- **目的**: L2・L3 のデータの形を決める。オフラインでの入力と前年からの引き継ぎができるようにする。
- **対象機能**: 最終目標の5・9。
- **保存するもの（案）**:
  - 物件、物件管理表、設備（物件 × 様式 × その番号 × 何番目か）
  - 点検（年度・機器／総合）、欄の値（欄 ID・値・出どころ・確認の状態）
  - 記号の値、備考、写真、指摘事項（未改善かどうか）
- **前年からの引き継ぎ**:
  - L2 は値を写す。
  - L3 は写さない。ただし前年の指摘事項のうち、未改善のものは「引き継ぐ候補」として見せる。
  - 総括表の措置内容は、空欄を原則とする（Q10。仕様を決める前に確認が必要。`05-gate-b-summary.md` の J1）。
- **既存システムとの関係（確かめる項目）**:
  - Supabase の今のテーブル
  - オフラインで保存する仕組み（IndexedDB など）と、同期のやり方
  - 写真の保存と、設備との関係
  - 今のデータを新しい形に移せるか
- **検証方法**: D5 で取り出したデータを保存し、D7 で出力した結果が元の PDF と合うこと（往復の試験）。
- **未解決事項**:
  - DB の構造の変更は今回は禁止。移行の計画は、承認の後に作る。
- **実装時の注意**: 欄の値には、テンプレートの版の番号を持たせる。テンプレートを直した後も、昔の出力を作り直せるようにする。

## D7 PDF の再生成（再記入）エンジン

- **目的**: 承認済みの白紙テンプレートに、L2・L3 の値を D4 の規則で記入する。元の PDF と同じ体裁で出力する。
- **対象機能**: 最終目標の6〜8。
- **流れ**:
  1. 白紙の PDF を写す（原本は使わない）。
  2. 欄ごとに配置を計算する（寸法・改行・縮小）。
  3. 文字と記号を描く。記号は、楕円・斜線をベクターで描く。
  4. はみ出し・重なりを調べる（D9）。
  5. 出力に版の番号を付けて保存する。
- **技術的な方法（案）**: pdf-lib と fontkit で、日本語のフォントをサブセットで埋め込む。記号は `drawEllipse`・`drawLine` に、実測した線の太さを渡して描く。
  - 計算した配置は、PDF を作る前に JSON で出し、検査できるようにする。
- **既存システムとの関係（確かめる項目）**:
  - 今の pdf-lib の処理（白紙の上に書いているか、帳票全体を描いているか）
  - フォントを埋め込んでいるか
  - PWA でオフラインのまま生成できるか（フォントの大きさ）
- **検証方法**: D9 の6つの比べ方。
- **未解決事項**:
  - フォント（Q7）。
  - 元の PDF と文字の層の構造（文字の順番・まとまり方）まで合わせるか、見た目だけ合わせるか（J4）。
- **実装時の注意**: 画像にして作り直さない。白で塗って隠さない。入りきらないときに、黙って縮小しない（記録を残す）。

## D8 出力と製本（消防署提出用・顧客提出用）

- **目的**: 提出先ごとに、ページの組み合わせ・順番・表示を自動でそろえる。
- **対象機能**: 最終目標の10、Q9。
- **ページの順番**:
  - 既存の点検報告書一式の並び（報告書 → 総括表 → 点検者一覧 → 各設備）を、帳票ファミリーの順として定義する。
  - 前に別のページがある 21件の型を調べ、例外として持つ。
- **2つの出力の違い**:
  - **消防署提出用**: 様式のとおり。
  - **顧客提出用**: 指摘のある欄を赤で示し、指摘事項の一覧を付ける。
  - 赤字は、yEgo が出力するときに付け加える。元の PDF の赤字の手書きは読み取らない。
- **押印**: 押印したもの・スキャンしたもの（印取原本）は、画像のページとして差し込める置き場にする。
- **既存システムとの関係（確かめる項目）**: 今の PDF をまとめる処理と、表紙・目次の有無。
- **検証方法**: 既存の点検報告書一式と、ページの数・順番・様式の並びを比べる。
- **未解決事項**:
  - 顧客提出用の赤字の書き方（色・線・注記の位置）（J9）。
  - 押印したページの扱い。
- **実装時の注意**: 製本した PDF にも、元の出力の版を記録する。作り直しても上書きしない。

## D9 品質検証とテスト

- **目的**: 再生成した PDF が正しいことを、数字で示す。
- **対象機能**: 最終目標の8。すべての設計書の合格の基準。
- **検査**:
  - **出力のたびに行う検査**: はみ出し（欄の枠の外）、重なり（文字どうし・文字と罫線・記号）、欠落（必須の欄が空）、二重の記入。
  - **テンプレートの合格の検査**: Gate A 報告書 10章の 1〜5（罫線・文字の層・記号・はみ出し・画像の差）。
  - **1物件を抜いて作る試験**: 評価用の 50 物件で行う。
- **閾値**: 10章の数値（±0.5pt・±0.3pt・0.99 など）は**仮の値**とする。最初の試験の実測の分布を見てから決め、利用者の承認を得る。
- **既存システムとの関係（確かめる項目）**: 今のテストの仕組み（Vitest・Playwright など）と、CI があるか。
- **検証方法**:
  - 検査そのものが正しいか: わざとずらした PDF を作り、検査が見つけるかを確かめる。
  - 差がある場所を色で示した画像で、目で確かめる。
- **未解決事項**:
  - 評価用の 50 物件の一覧（`01-exceptions.md` の8章）が、手元に無い。
- **実装時の注意**:
  - 顧客の PDF をテストのデータとしてリポジトリに置かない（J8）。
  - 検査の結果は、出力ごとに保存する。
