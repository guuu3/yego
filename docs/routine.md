# 定常運転の指示書（Claude Code の定期実行用）

三者（Claude Code / Codex / もち）がユーザーの手を介さずに回るための、
Claude Code 側の定期実行（claude.ai のスケジュール済みタスク＝Routine）
の指示。対象リポジトリは **guuu3/yego のみ**。

運転方式は**バトン方式**：セッションは1回ごとに終わるが、進捗の正本を
`docs/progress.md` に置き、各サイクルが必ず前回の続きから再開する。
サイクルの間隔を短くすることで、実質的に止まらず続いていく運転にする。

Routine のプロンプトには次の1行だけを入れる：

> guuu3/yego の docs/routine.md の指示に従って、定常運転を1サイクル実行してください

## 1サイクルでやること（順番固定）

1. **円卓の確認と記入**：`roundtable/` を確認し、自分の欄が未記入の
   議題があれば、他の作業の前に意見を書く。もちや Codex から自分宛の
   問いがあれば、それへの回答を優先する
2. **バトンを受け取る**：`docs/progress.md` を読み、「次にやること」
   から再開する。作業項目の優先はバトンの記載に従う（初回は
   `docs/first-run.md` の「最初の型の試作」、完了後は first-run.md
   末尾の優先順位、円卓で合意された作業があればそちらを優先）
3. **1単位をやり切る**：作業は「型1つ分の定義更新／再生成サンプル／
   一致の実測」など区切りの良い単位で進め、原則として1単位を
   やり切ってからサイクルを終える。時間や文脈の上限で単位の途中に
   なった場合は、そこまでの成果物を push し、バトンに「どこまで
   進み、残りは何か」を具体的に残す（次のサイクルが迷わず再開できる
   粒度で書く）
4. **円卓への報告**：進めた内容の要約と、判断が必要な点を、関係する
   議題の自分の欄（または新しい議題）に書く。もちへの確認事項は
   円卓に書けば、もちの定期チェック（1時間おき）が拾って応答する
5. **Codex レビューの取り込み**：PC ローカル実行で接続が効く場合は
   `/codex-review` で節目のレビューを受ける。クラウド実行では接続が
   効かないので、レビュー依頼を円卓に残す（Codex の応答は非同期で
   よく、作業は Codex 待ちで止めない）
6. **バトンを渡す**：サイクルの最後に必ず `docs/progress.md` を更新
   して push する（現在の作業項目／完了した単位／次にやること／
   停止中なら項目と理由）。バトンが古いまま終わるサイクルは失敗と
   みなす

## 止まる条件（first-run.md と共通）

- 規定様式との一致が取れないまま次工程に進まない。不一致は
  「どこが・どれだけ違うか」を記録して、その項目は止める
- 原本 PDF・完全版 CSV・顧客情報はリポジトリに入れない（検証は
  匿名化データのみ）
- `design/`（もち担当）は編集しない。設計変更の提案は円卓で出す
- ユーザーの決定が要る事項（合格条件の線引き、範囲の決定など）は
  勝手に決めず、円卓の論点として残す。もちが論点整理して
  ユーザーに上げる

## 運転のリズム

- Routine は短い間隔で回す（目安は3時間おき）。1回ごとのセッションは
  終わるが、バトンでつながるため実質的に継続運転になる。note 制作
  （09:00 の定期実行）とはリポジトリが別なので干渉しない
- バトン（`docs/progress.md`）が三者の共通の現在地になる。円卓は
  「議論と決定」の場、バトンは「作業の現在地」と役割を分ける
- もちは1時間おきに円卓とバトンを監視し、意見への応答・論点整理・
  合意案の作成と、節目でのユーザー報告を担う
- ユーザーが触るのは「決定」の欄と、合格条件など事業判断の
  承認だけ。それ以外の運搬・催促・転記は三者で回す
